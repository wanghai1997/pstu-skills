# PDF OCR Converter 技术故事

> **写给未来的自己**：这篇文档记录了我们如何从"一个简单想法"走到"能处理1000页论文的实用工具"的全过程。这里没有枯燥的术语堆砌，只有真实的踩坑记录和思考脉络。

---

## 一、故事的开端：被"图片"困住的文字

### 那个触发一切的场景

想象这样一个画面：你下载了一篇500页的学术专著，兴冲冲地打开 Claude，想让它帮你总结核心观点。结果 Claude 却说："抱歉，这是一个图片型PDF，我无法读取内容。"

你打开文件一看——确实是扫描版，每一页都是一张高清图片。文字清晰可见，但对于 AI 来说，就像让盲人欣赏油画一样——**看得见像素，读不懂含义**。

这就是我们要解决的问题：
> **如何让 AI 能"读懂"扫描版 PDF 里的文字？**

### 类比：就像给一本手抄书制作"隐形字幕"

想象一下 medieval 修道院的僧侣们手抄的圣经。书页泛黄，字迹优美，但现代人想搜索"摩西"出现在哪几页，只能一页页翻。

我们的任务，就像是给这本古籍添加一层"隐形的现代文字"——
- **表面上**：书还是那本书，图片、图表、排版原封不动
- **实际上**：每个字都变成了可搜索、可复制的数字文本

这就是 OCR（光学字符识别）技术的本质：**看见→识别→重构**。

## 二、技术架构演进：从"一把梭"到"流水线"

### 第一阶段：天真的一口气方案（基础版）

刚开始，我们以为这就是个"三步走"的简单问题：

```
PDF → 转成图片 → OCR识别 → 生成新PDF
```

代码写得很直接：
```python
# 基础版思路（适合<100页的小文件）
images = convert_from_path(pdf_file)  # 一次性全部转换
for image in images:
    text = pytesseract.image_to_string(image)  # 逐页OCR
    # ...生成PDF
```

**这个方案在什么情况下会崩溃？**

假设你处理一本1000页的博士论文，每页200 DPI高清扫描：
- 单页图片 ≈ 5MB
- 1000页全部加载到内存 = 5GB
- 加上OCR过程中的中间数据，轻松突破 8GB

**结果**：你的电脑开始疯狂swap，风扇像直升机起飞，最后 Python 抛出 `MemoryError`。

### 第二阶段：庖丁解牛的流水线城市（增强版）

于是我们意识到：**必须像工厂流水线一样，一次只处理一小批**。

#### 核心设计：批处理 + 断点续传

想象一个印刷厂收到1000本书的装订任务：

**愚蠢的做法**：把1000本书全部堆在车间，结果连下脚的地方都没有。

**聪明的做法**：
1. 每50本为一批
2. 完成一批，运走一批
3. 车间永远只保留50本的空间
4. 如果停电了，记住处理到第几批，来电后继续

这就是我们的核心架构：

```python
# 增强版：智能分批处理
total_batches = (1000 + 50 - 1) // 50  # = 20批

for batch_num in range(total_batches):
    start_page = batch_num * 50 + 1      # 第1页、第51页、第101页...
    end_page = min((batch_num + 1) * 50, total_pages)

    # 只加载这50页
    batch_images = convert_from_path(
        pdf_file,
        first_page=start_page,
        last_page=end_page
    )

    # 处理并保存为临时PDF
    process_and_save_batch(batch_images, f"batch_{batch_num}.pdf")

    # 清理内存
    del batch_images
```

**断点续传如何实现？**

每次完成一批，我们写一个"进度日记"：

```python
progress = {
    'input_file': 'thesis.pdf',
    'output_file': 'output.pdf',
    'last_batch': 7,           # 已完成第7批
    'batch_files': [           # 已生成的批次文件
        'batch_001.pdf',
        'batch_002.pdf',
        ...
        'batch_007.pdf'
    ],
    'timestamp': '2024-01-28T10:30:00'
}

# 保存到文件
with open('progress.json', 'w') as f:
    json.dump(progress, f)
```

如果用户按了 Ctrl+C，下次运行时带上 `--resume` 参数，程序就会读取这个日记，从第8批开始继续。

## 三、最棘手的挑战：图表和公式怎么办？

### 问题的本质

学术论文不是纯文本。里面有：
- 数据图表（柱状图、折线图、散点图）
- 数学公式（积分号、希腊字母、矩阵）
- 技术示意图（流程图、结构图）

如果我们简单粗暴地把所有内容OCR成纯文字：
- 图表变成一堆乱码文字描述
- 公式变成 "∫" 变成 "S"，"α" 变成 "a"
- 排版彻底混乱

**用户的核心需求**：转换后的PDF要能**搜索文字**，但**图表必须原样保留**。

### 解决方案："图层蛋糕"架构

想象 Photoshop 的图层概念：

```
┌─────────────────────────────────┐
│  图层1：原始页面图片（可见）      │  ← 图表、公式、排版原封不动
│  [图表][公式][文字扫描图]        │
├─────────────────────────────────┤
│  图层2：OCR文字层（透明但可选中） │  ← 只包含识别出的文字
│  [可搜索文字][可复制文字]        │
└─────────────────────────────────┘
```

**技术实现**（使用 PyMuPDF）：

```python
doc = fitz.open()
page = doc.new_page(width=img_width, height=img_height)

# 第一步：把原始图片作为"背景"
page.insert_image(
    fitz.Rect(0, 0, img_width, img_height),
    filename=img_path
)

# 第二步：在对应位置叠加"隐形文字"
for text_block in ocr_results:
    page.insert_text(
        fitz.Point(text_block['x'], text_block['y']),
        text_block['text'],
        fontsize=text_block['height'] * 0.8,
        color=(0, 0, 0),      # 黑色
        overlay=True          # 叠加在图片之上
    )
```

**关键技巧**：文字是**可见但透明的**吗？不，实际上：
- 文字颜色设为黑色（可见）
- 但由于图片也在同一位置，用户视觉上看到的是图片上的文字
- 搜索时，PDF阅读器能"看到"这层文字
- 选中复制时，复制的是这层文字，而不是图片

### 图表区域的智能识别

如何判断哪里是图表、哪里是文字？

我们使用**启发式规则**：

```python
def detect_figures_and_tables(page_structure):
    special_regions = []

    for block in page_structure['text_blocks']:
        if block['type'] == 'image':
            # PyMuPDF 识别出的图片区域
            special_regions.append({
                'type': 'figure',
                'bbox': block['bbox']  # 边界框坐标
            })

    return special_regions
```

在OCR时，**跳过**图表区域内的文字识别（反正也不准），直接保留原图。

## 四、我们踩过的坑（以及爬出来的方法）

### 坑1：Windows 的 Unicode 噩梦

**症状**：程序跑到一半报错：
```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2713' in position 0
```

**原因**：我们在代码里用了 `✓` 和 `✗` 这些漂亮的符号表示成功/失败。但 Windows 的命令行默认编码是 GBK，不认识这些 Unicode 字符。

**修复**：把所有 Unicode 符号换成 ASCII 安全版本：
```python
# 修改前
print("✓ 处理完成")

# 修改后
print("[OK] 处理完成")
```

**教训**：在跨平台工具中，输出信息坚持用 ASCII 字符集，不要因为"美观"而牺牲兼容性。

### 坑2：Tesseract 的安装地狱

**症状**：运行程序报错：
```
pytesseract.pytesseract.TesseractNotFoundError: tesseract is not installed or it's not in your PATH
```

**原因**：Tesseract 是 Google 开发的 OCR 引擎，但它**不会随 Python 包一起安装**。用户必须：
1. 单独下载安装程序
2. 记住安装路径
3. 配置环境变量

**修复**：在 SKILL.md 中写了详细的安装指南，并提供检测脚本：

```python
def check_tesseract():
    try:
        version = pytesseract.get_tesseract_version()
        return True, f"版本: {version}"
    except:
        return False, "未安装或未配置PATH"
```

**教训**：依赖外部二进制程序时，必须提供：
- 各平台的安装指南
- 自动检测脚本
- 清晰的错误提示（不只是抛异常，要告诉用户"去哪下载、怎么配置"）

### 坑3：DPI 的迷雾

**症状**：用户抱怨"OCR准确率太低，很多字识别错了"。

**调查**：发现用户用的PDF扫描质量很差，只有 72 DPI（屏幕分辨率）。

**原理**：OCR 引擎需要足够的像素信息来"看清"文字。DPI（每英寸点数）决定了：
- 72 DPI：网页图片质量，文字边缘模糊
- 200 DPI：标准打印质量，文字清晰
- 300 DPI：高精度，适合小字体

**修复**：默认使用 200 DPI，并提供 `--dpi` 参数让用户根据需求调整。

```python
# 质量 vs 速度 的权衡表
DPI_OPTIONS = {
    150: "快速预览，适合草稿",
    200: "推荐默认值，平衡质量与速度",
    300: "高精度，适合学术论文",
    400: "超高清， rarely needed"
}
```

**教训**：不要假设所有输入都是"标准质量"。文档型工具必须暴露"质量控制"参数给用户。

### 坑4：内存泄漏的幽灵

**症状**：处理大文件时，即使分批处理，内存占用还是缓慢增长，最终崩溃。

**调查**：发现 PIL（Pillow）图片对象没有被及时释放。

```python
# 有问题的代码
for page_num in range(start, end):
    img = convert_page_to_image(page_num)
    process(img)
    # img 还在内存里！

# 修复后的代码
for page_num in range(start, end):
    img = convert_page_to_image(page_num)
    process(img)
    img.close()  # 显式关闭
    del img      # 删除引用
```

**教训**：Python 虽然有垃圾回收，但对于大对象（图片、文件句柄），**显式清理**比依赖 GC 更可靠。

### 坑5：坐标系统的混乱

**症状**：文字位置偏移，OCR出的文字和原图对不上。

**原因**：不同库的坐标系统不同：

| 库 | 坐标原点 | Y轴方向 |
|----|---------|--------|
| PIL/Pillow | 左上角 | 向下增加 |
| Tesseract | 左上角 | 向下增加 |
| PyMuPDF/reportlab | 左下角 | 向上增加 |

**修复**：使用 PyMuPDF 时，Y坐标需要翻转：
```python
# 转换Y坐标（翻转）
y_pdf = page_height - y_tesseract
```

## 五、技术选型背后的思考

### 为什么选择 Tesseract？

市面上有很多 OCR 方案：

| 方案 | 优点 | 缺点 | 我们的选择 |
|------|------|------|-----------|
| Tesseract | 开源免费，支持100+语言 | 准确率中等 | ✅ 选用 |
| 百度/腾讯/阿里 OCR API | 准确率高，支持复杂排版 | 收费，需联网，有隐私风险 | ❌ 排除 |
| PaddleOCR | 中文效果好，开源 | 模型体积大，部署复杂 | ❌ 暂缓 |

**核心考量**：
1. **隐私优先**：学术文档往往涉及未发表的研究，不能上传到第三方服务器
2. **离线可用**：用户可能在无网络环境（如图书馆、飞机上）使用
3. **成本**：研究生没有预算支付 API 费用

### 为什么选择 PyMuPDF（fitz）？

PDF 处理库有很多选择：

| 库 | 定位 | 我们的用途 |
|----|------|-----------|
| PyPDF2 | 纯Python，轻量 | 简单读写，不适合复杂操作 |
| pdf2image | PDF转图片 | ✅ 用于OCR前的图片生成 |
| PyMuPDF (fitz) | 功能全面，性能强 | ✅ 用于精细PDF操作（文字层叠加、合并） |
| reportlab | 生成PDF | 最初考虑，但无法方便地叠加文字层 |

PyMuPDF 的关键优势：`page.insert_text()` 方法让我们能在指定坐标精确放置文字，而且支持 **overlay 模式**（文字浮于图片之上）。

## 六、优秀工程师的思维方式

通过这次项目，我们体会到几个重要的工程思维：

### 1. 失败模式先行（Think About Failure First）

不是问"正常情况下它怎么工作"，而是问：
- 如果用户传入1000页文件怎么办？
- 如果处理到一半断电了怎么办？
- 如果用户的电脑只有4GB内存怎么办？

**我们的应对**：批处理 + 断点续传 + 内存清理

### 2. 渐进式增强（Progressive Enhancement）

不是一次性做完美，而是先做一个"能用"的版本，再逐步优化：

- **MVP**（最小可行产品）：能处理10页PDF
- **增强版**：支持1000页，保留图表
- **未来版**：公式LaTeX识别、表格结构化提取

### 3. 用户反馈是设计的一部分

程序不只是"跑完就完"，要让用户**感知进度**：

```python
# 不好的反馈
process_pdf()  # 10分钟后才结束，用户以为卡死了

# 好的反馈
print("[INFO] 分析PDF结构: 1000页，将分20批处理")
for i in range(20):
    print(f"[INFO] 处理批次 {i+1}/20...")
    process_batch(i)
print("[OK] 完成！")
```

### 4. 防御性编程（Defensive Programming）

假设用户会犯错，提前检查：

```python
# 检查输入文件存在
if not os.path.exists(input_path):
    raise FileNotFoundError(f"找不到文件: {input_path}")

# 检查Tesseract安装
try:
    pytesseract.get_tesseract_version()
except:
    print("[ERROR] Tesseract未安装，请参见安装指南...")
    sys.exit(1)
```

## 七、两个版本的对比：基础版 vs 增强版

我们为不同场景提供了两个版本：

| 特性 | 基础版 (`ocr_pdf_basic.py`) | 增强版 (`ocr_pdf_advanced.py`) |
|------|---------------------------|------------------------------|
| **适用场景** | 小文件 (<100页) | 大文件 (500-1000页) |
| **内存占用** | 随页数线性增长 | 固定 (~500MB-1GB) |
| **批处理** | ❌ | ✅ 默认50页/批 |
| **断点续传** | ❌ | ✅ `--resume` 支持 |
| **图表保留** | 基础保留 | 智能检测和保留 |
| **进度保存** | ❌ | ✅ 每批自动保存 |
| **速度** | 快（无额外开销） | 略慢（有合并步骤） |
| **代码复杂度** | 简单（~200行） | 复杂（~600行） |

**选择建议**：
- 处理论文、书籍章节（<100页）：用基础版
- 处理专著、大部头（>500页）：用增强版
- 不确定文件大小：直接用增强版（它也能处理小文件）

## 八、最佳实践清单

如果你要基于这个项目继续开发，请记住：

### 代码层面
- ✅ 所有文件操作使用 `with` 语句或显式关闭
- ✅ 每批处理后调用 `gc.collect()` 建议垃圾回收
- ✅ 临时文件统一放在 `tempfile.mkdtemp()` 创建的目录
- ✅ 异常处理时清理资源（`try-finally` 或上下文管理器）

### 用户体验层面
- ✅ 提供进度反馈（批次数、页数、预计时间）
- ✅ 支持 `--resume` 断点续传
- ✅ 出错时告诉用户"为什么"和"怎么办"，不只是报错信息
- ✅ 提供 `--keep-temp` 调试模式，方便排查问题

### 性能优化
- ✅ 默认DPI 200（平衡质量与速度）
- ✅ 默认批次50页（适合8GB内存电脑）
- ✅ 使用 `tqdm` 显示进度条
- ✅ 大文件优先处理，避免小文件拖慢整体进度

## 九、未来的路

这个项目已经能解决"大文件OCR转换"的核心问题，但还有可以改进的方向：

### 短期可做的
1. **多线程处理**：同一批次内多页并行OCR（Tesseract支持多线程）
2. **PDF/A 标准**：生成符合长期存档标准的PDF/A格式
3. **元数据保留**：保留原PDF的书签、作者、标题信息

### 中期探索
1. **LaTeX公式识别**：集成 pix2tex 等工具，把公式转成可编辑的LaTeX代码
2. **表格结构化**：不只是保留图表图片，而是提取成 CSV/Excel
3. **版面分析**：自动识别双栏、三栏排版，保留阅读顺序

### 长期愿景
做一个"AI论文阅读助手"的完整工作流：
```
扫描版PDF → OCR转换 → 结构化解构 → AI总结 → 知识图谱生成
```
